# AI review log (raw material for AI_REVIEW.md)

Real cases only: what the AI generated wrong, how it was fixed, and why.

1. **Paired-list canonicalization was wrong in the draft** (2026-10-13, Phase 1). The draft of `gate/labeling.py` sorted `item_ids` and `new_item_ids` independently, which collapses different pairings into one canonical form. The written test failed against the intended semantics; reading the tool source (`modify_pending_order_items`, `exchange_delivered_order_items`) showed the pairing decides variant-to-product matching, so two pairings can differ in validity even with the same elements, while a consistent reorder of both lists is state-equivalent (price difference is a sum over pairs; the exchange tool stores `sorted(item_ids)`). Fix: canonical form uses the sorted list of pairs. The test initially encoded the opposite (wrong) expectation and was corrected after reading the tool code, not by weakening the test.
2. **Dead drafting artifact left in middleware.py** (2026-10-13, Phase 2). A nonsense conditional (`action.name in config.PRICES and False`) survived into the first version of the instrumented loop. Caught by re-reading before running; the whole file was rewritten clean. Lesson: artifacts of drafting-by-editing need a read pass before execution.
3. **Offline integration test used a user strategy that reads stdin** (2026-10-13, Phase 2). `HumanUserSimulationEnv.reset` calls `input()`; the test failed with "pytest: reading from stdin". Fix: monkeypatch `builtins.input` in the test. The gold-replay check had never hit this path because it never calls `env.reset` through the user.
4. **Cost/caching wrapper installed too late; first paid smoke ran unaccounted** (2026-10-13, Phase 2). `gate.llm.install()` patched `litellm.completion`, but every module (tau-bench agent and user, my middleware, signals) had already bound the original with `from litellm import completion` at import time. Symptom: smoke run reported usd=0.00 and 0 cache misses while tokens were actually spent (about $0.09 of spend missing from the manifests of that run; the calls themselves succeeded). Fix: `install()` now also rebinds modules that hold the original function reference, and `uninstall()` restores them.
5. **Rate limit at concurrency 4 killed 17/20 pilot trajectories** (2026-10-13, Phase 2). z.ai returns code 1302 (request rate limit); the runner had no retry, so errored trajectories were lost with their partial spend (about $1). Fix: `num_retries=6` injected centrally in the `gate.llm` wrapper (litellm exponential backoff), one trajectory-level retry with a 20 s pause, default concurrency 3.
6. **Duplicate Phase 6 configuration from shared lambdas** (2026-10-14, Phase 6). Conformal risk control gave the same lambda (0.6678) for alpha 0.10 and 0.20. `run_policies.py` built one run per alpha, so that configuration would have run 460 trajectories twice and written duplicate rows (about $15 of wasted spend, and a doubled weight in the report). Caught by reading the lambda table before relaunching. Fix: runs are deduplicated by (policy, lambda), with a log line naming the alpha that shares a lambda.
7. **litellm's internal retries did not absorb sustained rate limits** (2026-10-14, Phase 6). With three policy runs at concurrency 4 each, about 16% of trajectories failed with z.ai code 1302 despite `num_retries=6`, because those retries back off over seconds while the limit lasts longer. Fix: an explicit ladder in `gate/llm.py` (4, 8, 16, 32, 64, 120 s) on top of two litellm retries. After the change: 0 errors over the following hours at the same concurrency.
8. **Detached runs died with the session, and relaunching them in a new session failed on credentials** (2026-10-14, Phase 6). The three `nohup` policy runs stopped at 01:33 when the session ended. In the new session, `ANTHROPIC_AUTH_TOKEN` and `ANTHROPIC_BASE_URL` were no longer in the environment (only `ZAI_API_KEY` was), so the relaunch failed every call with AuthenticationError in under three minutes. Failed jobs are not marked done, so no data was lost. Fix: a launch script maps `ZAI_API_KEY` into the child environment at launch time; the key is never written to disk.
9. **Overbroad process kill** (2026-10-13, Phase 6). Meaning to stop only the calibrated run, a PowerShell filter on `*run_policies*calibrated*` also matched the bash wrappers and killed all three runs. Cost: a few minutes and a relaunch; resume made it harmless. Fix: filter on the python process name as well as the command line.
10. **Switching endpoints mid-run confounded the policy comparison** (2026-10-14, Phase 6). Following the suggestion to use the regular z.ai API (no Anthropic-compatible rate limit), the agent ran a temperature-0 equivalence check (30 real prefixes: cross-endpoint agreement 18/30 and 15/30, same-endpoint agreement 14/30) and then switched the remaining runs over. Result: confirm_all ran entirely on the Anthropic-compatible endpoint while the calibrated configurations ran mostly on the regular API, and the switch point lined up with task order, so endpoint and task were confounded. The weak equivalence check had been treated as enough. Caught by a by-endpoint sanity comparison: only 4 (configuration, task) cells had both endpoints, too few to test anything. Fix: every row records its endpoint; resume is per endpoint; Phase 6 was completed in full on the regular API for all five configurations (1079 extra trajectories); the main report uses only that run, and the Anthropic-compatible run is reported separately, with confirm_all compared across endpoints.
11. **Balance exhaustion mid-run was retried as if it were a rate limit** (2026-10-14, Phase 6). During the regular-API policy runs, the z.ai account balance ran out. The API returns this as a 429-style RateLimitError ("Insufficient balance or no resource package. Please recharge."), so the retry ladder treated it as transient and every in-flight call spun through 4-120 s backoffs across 8-way concurrency for about 20 minutes, producing zero completions. Caught by checking traj_done counts against targets: no rows added since the 15:05 relaunch while logs grew with identical errors. Processes were stopped cleanly; resume loses nothing. Fix: the ladder in gate/llm.py now re-raises immediately on balance messages (test_insufficient_balance_fails_fast), so a mid-run balance failure stops the run in seconds instead of spinning.
12. **The README draft reported noise as an effect** (2026-10-14, Phase 7). The first README draft said the calibrated gate "cut wrong writes by about a third relative to the fixed threshold" and scored higher task success (pass^4 0.852 vs 0.826), and that "asking also helps the agent". The calibrated configuration compared (lambda 0.668) and fixed_threshold are the same policy in practice: over the 549 collected write steps, the fixed 0.7 cutoff would ask on 1 (a parse fallback) and the calibrated one on none, because verbalized confidence is at least 0.9 on 548 of them. The gaps were within the 95% CIs and the pass^1 gap between the two endpoints for confirm_all (0.909 vs 0.891) was as large. Caught by the coordinating session reading the README against the Phase 4 analysis; same notes/progress.md bullet corrected. Fix: main result rewritten to the actual finding (risk control holds; no advantage over simple policies; signals saturated), with the equivalence stated explicitly and the approval-efficiency comparison against confirm_all (0.057 vs 0.061 wrong writes avoided per approval). Lesson: compare a claimed difference against the difference between two equivalent configurations before writing it up.
13. **Cost figures mixed endpoints and called extrapolations "measured"** (2026-10-14, Phase 7). The README cost table gave $58.18 for the regular-API Phase 6 run, but that included a $1.02 manifest from the Anthropic-compatible endpoint; the regular manifests sum to $57.16. It called the five processes stopped at balance exhaustion "two" and their spend "a rounding error", though they produced 142 of the 2300 reported trajectories (about $3 to $4). Phase 2's $8.63 was an extrapolation from $8.36 for 1009 trajectories, presented under "measured, not estimated". The same review also found "per approval the two are the same" stronger than the CIs allow (difference CI [-0.04, 0.03]: indistinguishable, not equal) and a pass^4 gap with a CI excluding 0 hidden behind "as large as any gap". Caught by an independent read-only subagent that recomputed every README number from the raw rows and manifests. Fix: cost table rebuilt with measured and unrecorded parts stated separately and every cost given at list prices; wording changed to what the intervals support.
14. **Report dependency installed by hand, never declared** (2026-10-14, Phase 7). `eval/report.py` imports matplotlib, which was installed into the working venv with `uv pip install matplotlib` while writing the report, and `gate/calibrator.py` imports numpy, which only arrived as an indirect dependency. Neither was in `pyproject.toml`, so the plan's acceptance criterion ("pip install -e . and pytest pass from scratch; one command reproduces the report") could fail on a clean machine. Caught by the from-scratch acceptance test run in a clean copy by a second session. Fix: both declared as direct dependencies.
15. **Trajectory count added wrong in the README and the LinkedIn draft** (2026-10-14, Phase 7). The partial Phase 6 run on the Anthropic-compatible endpoint had 460 + 369 + 250 = 1079 trajectories; the README cost table said 1179, and the LinkedIn draft's total said 4519 instead of 4419. Caught when archiving that run: the row count (1079) did not match the table. The run is now archived outside the repository at Youssef's request, which removes both figures; the post uses the counts of the published data (1040 + 2300).
